# Проект отказоустойчивого развертывания n8n с балансировкой и мониторингом

Данный проект представляет собой комплексное решение для запуска двух экземпляров **n8n** (платформы для автоматизации рабочих процессов) с балансировкой нагрузки через **Nginx**, общей базой данных **PostgreSQL**, а также полноценным мониторингом на базе **Prometheus**, **Grafana** и **Alertmanager**.  

Основная цель — обеспечить высокую доступность, масштабируемость и наблюдаемость системы. В рамках проекта описан процесс локального развертывания (на собственном сервере или виртуальной машине) и последующей миграции в облако **Yandex Cloud** с использованием управляемой БД (Managed Service for PostgreSQL) и организацией резервного копирования на **AWS S3**.

---

## 1. Развертывание на локальном ресурсе

Перед миграцией в облако необходимо развернуть и отладить систему локально. Это позволяет проверить работоспособность всех компонентов и подготовить конфигурации.

### 1.1. Docker

Для контейнеризации используется **Docker** и **Docker Compose**. Убедитесь, что на вашей машине установлены:
- Docker (версия 20.10+)
- Docker Compose (версия 2.x)

Создайте файл `docker-compose.yml` со следующим содержимым (ключевые сервисы: n8n1, n8n2, nginx):

```yaml
version: '3.8'

services:
  n8n1:
    image: n8nio/n8n:latest
    container_name: n8n_instance_1
    environment:
      - DB_TYPE=postgresdb
      - DB_POSTGRESDB_HOST=postgres
      - DB_POSTGRESDB_PORT=5432
      - DB_POSTGRESDB_DATABASE=n8n
      - DB_POSTGRESDB_USER=n8n_user
      - DB_POSTGRESDB_PASSWORD=your_password
      - N8N_METRICS=true
    # ... остальные параметры

  n8n2:
    # аналогично

  nginx:
    image: nginx:alpine
    # ... конфигурация балансировщика

  # Далее сервисы мониторинга (будут описаны в п.1.3)
```

Не забудьте создать файл конфигурации Nginx с настройками upstream для двух инстансов n8n и включить `stub_status` для сбора метрик.

### 1.2. PostgreSQL

В локальной среде можно запустить PostgreSQL также в контейнере или использовать уже работающий экземпляр. Для совместимости с будущей облачной БД используйте PostgreSQL версии 15.

Пример запуска через Docker Compose:

```yaml
postgres:
  image: postgres:15
  environment:
    POSTGRES_DB: n8n
    POSTGRES_USER: n8n_user
    POSTGRES_PASSWORD: your_password
  volumes:
    - pg_data:/var/lib/postgresql/data
```

Перед первым запуском n8n необходимо создать базу данных и пользователя (если они не были созданы автоматически).

### 1.3. Мониторинг

Стек мониторинга включает:

- **Prometheus** — сбор метрик с n8n (эндпоинт `/metrics`) и Nginx (через `nginx-exporter`).
- **Grafana** — визуализация дашбордов.
- **Alertmanager** — отправка уведомлений при срабатывании правил.

Фрагмент `docker-compose.yml` для мониторинга:

```yaml
nginx-exporter:
  image: nginx/nginx-prometheus-exporter:latest
  command: ['-nginx.scrape-uri=http://nginx:80/stub_status']

prometheus:
  image: prom/prometheus:latest
  volumes:
    - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml
    - prometheus_data:/prometheus

grafana:
  image: grafana/grafana:latest
  environment:
    - GF_SECURITY_ADMIN_PASSWORD=admin
  volumes:
    - ./grafana/provisioning:/etc/grafana/provisioning

alertmanager:
  image: prom/alertmanager:latest
  volumes:
    - ./alertmanager/alertmanager.yml:/etc/alertmanager/alertmanager.yml
```

Не забудьте настроить файлы `prometheus.yml` (правила сбора и алерты), `alertmanager.yml` (получатели уведомлений) и подготовить дашборды Grafana (можно использовать готовые или создать свои).

## 2. Перенос на хостинг

После успешной локальной эксплуатации наступает этап миграции в облако. Мы выбрали **Yandex Cloud** по ряду причин, описанных ниже.

### 2.1. Сравнительный анализ двух хостингов

Перед выбором облачного провайдера мы провели сравнение двух популярных российских платформ: **Selectel** и **Yandex Cloud**. Оба предлагают управляемые базы данных, виртуальные машины и объектные хранилища. Ключевые критерии оценки:

- **Модель ценообразования**: возможность долгосрочного резервирования ресурсов со скидкой.
- **Стоимость аналогичной конфигурации** (4 vCPU, 8 GB RAM, 50 GB SSD для БД и аналогичная ВМ для приложений).
- **Удобство интеграции** с внешними сервисами (например, с AWS S3 для бэкапов).
- **Надёжность и доступность** (SLA, возможность географического резервирования).

Подробные актуальные цены можно найти на официальных сайтах:
- [Тарифы Selectel](https://selectel.ru/services/cloud/compute/tariffs/)
- [Тарифы Yandex Cloud](https://cloud.yandex.ru/prices)

**Обоснование выбора Yandex Cloud**:
- Более гибкая система скидок (CVoS — резервирование объёмов на 6–12 месяцев позволяет экономить до 22%).
- Встроенная возможность создания резервных копий в объектное хранилище (в том числе в AWS S3 через совместимый API).
- Удобный механизм пулера соединений для PostgreSQL (порт 6432), что снижает нагрузку на базу.
- По результатам тестов производительности и соотношения цена/качество Yandex Cloud оказался предпочтительнее для нашего сценария.

### 2.2. Выбор хостинга

Исходя из анализа, окончательное решение — **Yandex Cloud**. Для работы мы используем следующие сервисы:

- **Yandex Managed Service for PostgreSQL** — отказоустойчивый кластер из двух хостов (мастер и реплика) в разных зонах доступности.
- **Yandex Compute Cloud** — виртуальная машина для запуска Docker-контейнеров с n8n, Nginx и мониторингом.
- **Yandex Object Storage** (совместимый с AWS S3) — для хранения резервных копий базы данных и конфигураций.
- **Yandex VPC** — для сетевой изоляции и безопасности.

### 2.3. Перенос базы данных

Миграция данных выполняется с минимальным простоем с помощью утилит `pg_dump` / `pg_restore`. Для ускорения процесса и обеспечения целостности используется следующий алгоритм:

1. **Подготовка целевой БД** в Yandex Cloud через Terraform (код доступен в директории `terraform`).
2. **Скачивание корневого сертификата** Yandex для SSL-подключения.
3. **Создание дампа локальной БД** в формате `custom`.
4. **Восстановление дампа** в кластер Yandex Cloud с опциями `--clean --if-exists --no-owner`.
5. **Проверка данных** (количество таблиц, записи).

Все шаги автоматизированы в скрипте `scripts/01-migrate-data.sh`. Перед запуском убедитесь, что в `.env` указаны корректные параметры подключения к локальной и целевой БД.

### 2.4. Перенос сервисов

После того как база данных перенесена, необходимо развернуть Docker-стек на виртуальной машине в Yandex Cloud. Для этого:

1. Создайте ВМ с помощью Terraform (`vm.tf`) с предустановленными Docker и Docker Compose (через `user-data`).
2. Скопируйте на ВМ все необходимые конфигурационные файлы (`docker-compose.yml`, `.env`, `nginx.conf`, файлы для мониторинга).
3. Запустите стек командой `docker-compose up -d`.

Скрипт `scripts/02-deploy-stack.sh` автоматизирует этот процесс: подключается к ВМ по SSH, копирует файлы и запускает контейнеры.

### 2.5. Тестирование

После развёртывания необходимо провести функциональное тестирование:

- Проверить доступность веб-интерфейса n8n через балансировщик (порт 80).
- Создать тестовый workflow и убедиться, что он выполняется.
- Проверить, что webhook'и корректно обрабатываются.
- Убедиться, что все метрики поступают в Prometheus, а дашборды Grafana отображают актуальные данные.
- Протестировать отправку алертов (например, временно остановить один из экземпляров n8n и проверить, приходит ли уведомление в Telegram).

Для автоматизации проверок можно использовать скрипт `scripts/04-check.sh`, который выполняет HTTP-запросы к ключевым эндпоинтам.

### 2.6. Мониторинг

После переноса важно адаптировать мониторинг под новую инфраструктуру:

- В `prometheus.yml` изменить цели (targets) на новые имена хостов или IP-адреса.
- Настроить оповещения (Alertmanager) для отслеживания состояния кластера PostgreSQL (например, через `postgres-exporter`, если развёрнут).
- Импортировать дашборды Grafana, учитывая новые источники данных.

Мы используем **Grafana provisioning** для автоматического добавления дашбордов при старте контейнера — это гарантирует воспроизводимость конфигурации.

### 2.7. Организация Backup на AWS

Резервное копирование критически важно для любой production-системы. В качестве дополнительного уровня защиты мы настроили выгрузку резервных копий в **AWS S3** (или совместимое хранилище, например Yandex Object Storage). План бэкапов:

- **Полный дамп PostgreSQL** — ежедневно.
- **Архивация конфигурационных файлов** и `docker-compose.yml` — при каждом изменении.
- **Хранение копий за последние 30 дней** с возможностью более длительного хранения для аудита.

Реализация:

1. Создайте бакет в Yandex Object Storage (или AWS S3) с соответствующими правами доступа.
2. Настройте политику жизненного цикла для автоматического удаления старых бэкапов.
3. Используйте скрипт `backup.sh`, который:
   - Создаёт дамп БД с помощью `pg_dump`.
   - Сжимает дамп и конфигурацию в архив.
   - Загружает архив в S3 с помощью `awscli` (или `s3cmd`).
4. Запланируйте выполнение скрипта через cron.

Пример команды для загрузки в Yandex Object Storage (совместимый с AWS S3):

```bash
aws s3 cp backup.tar.gz s3://your-bucket/n8n-backups/ --endpoint-url=https://storage.yandexcloud.net
```

Не забудьте настроить переменные окружения `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY` для доступа к хранилищу.

## 3. Ролевая модель и управление доступом

Для обеспечения безопасной и эффективной эксплуатации системы важно чётко определить роли пользователей и администраторов, а также разграничить их права доступа к компонентам инфраструктуры. Ниже описаны основные роли, их обязанности и уровни привилегий.

### 3.1. Роли в системе n8n

| Роль | Обязанности | Права доступа |
|------|-------------|---------------|
| **Пользователь (User)** | Создание и запуск рабочих процессов (workflows), использование веб-хуков, интеграция с внешними сервисами. | Доступ к веб-интерфейсу n8n (через браузер). Может управлять только своими workflows, переменными и учетными данными. Не имеет доступа к настройкам системы и другим пользователям. |
| **Администратор n8n (n8n Admin)** | Управление пользователями (добавление/блокировка), настройка глобальных переменных, управление шаблонами, просмотр логов и статистики. | Полный доступ ко всем функциям n8n, включая раздел «Пользователи», «Настройки», «Аудит». Может изменять конфигурацию через переменные окружения (например, параметры аутентификации). |

> **Примечание:** В n8n разграничение прав реализуется через встроенную систему пользователей (в версии Enterprise доступны более детальные роли). В данном проекте используется community-версия, поэтому администратор фактически имеет все права.

### 3.2. Роли в управлении базой данных PostgreSQL

| Роль | Обязанности | Права доступа |
|------|-------------|---------------|
| **Администратор БД (DBA)** | Обслуживание PostgreSQL: настройка параметров, мониторинг производительности, управление резервными копиями, оптимизация запросов. | Полный доступ к СУБД (суперпользователь) – может создавать/удалять базы, пользователей, изменять конфигурацию, выполнять любые SQL-запросы. |
| **Приложение (n8n)** | Подключение к базе данных для чтения/записи данных workflows. | Выделенный пользователь БД (например, `n8n_user`) с правами на подключение, SELECT, INSERT, UPDATE, DELETE к схемам `public` и `n8n`. Не имеет прав на создание новых баз и пользователей. |

В облачной версии (Yandex Managed Service for PostgreSQL) администратор БД не имеет доступа к хостам (ОС), только к самой СУБД через SQL. Управление инфраструктурой БД (масштабирование, бэкапы) возлагается на DevOps-инженера через консоль облака.

### 3.3. Роли в инфраструктуре (Docker, Nginx, облако)

| Роль | Обязанности | Права доступа |
|------|-------------|---------------|
| **DevOps-инженер** | Развертывание и поддержка инфраструктуры: управление Docker-контейнерами, настройка Nginx, обновление сервисов, мониторинг ресурсов, управление облачными ресурсами (Yandex Cloud). | Доступ по SSH к виртуальной машине, управление Docker (docker-compose), доступ к панели управления Yandex Cloud (роль `editor` или `admin`), работа с Terraform. |
| **Администратор безопасности** (опционально) | Контроль безопасности: управление SSL-сертификатами, настройка firewall, аудит доступа, управление IAM в облаке. | Ограниченный доступ к критичным компонентам: панель управления облаком (роль `auditor`/`admin`), управление секретами (например, в Yandex Lockbox), просмотр логов безопасности. |

В рамках проекта DevOps-инженер также отвечает за настройку мониторинга и резервного копирования (см. ниже).

### 3.4. Роли в системе мониторинга

#### Prometheus / Alertmanager

| Роль | Обязанности | Права доступа |
|------|-------------|---------------|
| **Администратор мониторинга** | Настройка правил сбора метрик (scrape configs), создание и редактирование алертов, управление Alertmanager (настройка получателей уведомлений). | Доступ к файлам конфигурации Prometheus и Alertmanager (на ВМ), возможность перезагрузки конфигурации (`POST /-/reload`). Чтение метрик через веб-интерфейс Prometheus (обычно без аутентификации, но может быть защищено). |
| **Оператор** | Просмотр текущего состояния системы, анализ алертов, ручная проверка метрик. | Доступ к веб-интерфейсу Prometheus (если открыт) и Grafana (только чтение дашбордов). |

#### Grafana

| Роль | Обязанности | Права доступа |
|------|-------------|---------------|
| **Редактор (Editor)** | Создание и редактирование дашбордов, добавление источников данных. | Может изменять визуализации, но не управлять пользователями и плагинами. |
| **Администратор (Admin)** | Полный контроль над Grafana: управление пользователями, организациями, плагинами, системными настройками. | Доступ к разделу «Server Admin» и всем функциям. |
| **Зритель (Viewer)** | Просмотр существующих дашбордов без возможности изменений. | Только чтение. |

Рекомендуется создать в Grafana учётные записи для разных групп пользователей, используя внешнюю аутентификацию (например, через Google OAuth или LDAP), если требуется строгое разграничение.

### 3.5. Роли в резервном копировании (AWS S3 / Yandex Object Storage)

| Роль | Обязанности | Права доступа |
|------|-------------|---------------|
| **Администратор бэкапов** | Настройка политик резервного копирования, управление скриптами выгрузки, восстановление данных из бэкапов. | Доступ к сервису Object Storage (ключи доступа с правами на запись/чтение в конкретном бакете). Может просматривать и удалять старые бэкапы. |
| **Аудитор** | Проверка целостности и наличия бэкапов, тестирование восстановления. | Доступ только на чтение к бакету (например, через отдельный IAM-пользователь с правами `GetObject` и `ListBucket`). |

### 3.6. Принципы безопасности и разграничения доступа

1. **Минимально необходимые привилегии (PoLP)** – каждый пользователь/сервис получает только те права, которые необходимы для выполнения его функций.
2. **Использование отдельных учётных записей** – для административных действий (например, DevOps) применяются персональные аккаунты в облаке, а не общие.
3. **Сетевое изоляция** – доступ к БД разрешён только с ВМ приложений (через security groups), а к мониторингу – с ограниченных IP-адресов администраторов.
4. **Шифрование данных** – все соединения с БД и внешние webhook'и используют TLS. SSL-сертификаты хранятся в защищённом месте.
5. **Аудит действий** – в Yandex Cloud включён сервис Audit Trails для отслеживания изменений инфраструктуры. В n8n (Enterprise) доступен лог действий пользователей.

### 3.7. Пример матрицы доступа для типовых сотрудников

| Сотрудник           | n8n (UI) | PostgreSQL | ВМ (SSH) | Yandex Cloud Console | Grafana | Бэкапы (S3) |
|---------------------|----------|------------|----------|----------------------|---------|-------------|
| Бизнес-пользователь | ✔️ чтение/запись своих процессов | – | – | – | – | – |
| Администратор n8n   | ✔️ полный | – | – | – | – | – |
| DevOps-инженер      | – | ✔️ (через приложение) | ✔️ | ✔️ (роль `editor`) | ✔️ (admin) | ✔️ (чтение/запись) |
| DBA                 | – | ✔️ (SQL) | – | – | ✔️ (viewer) | ✔️ (чтение) |
| Аудитор             | – | – | – | ✔️ (роль `auditor`) | ✔️ (viewer) | ✔️ (чтение) |

> Данная матрица является рекомендуемой и может быть адаптирована под конкретные требования организации.

- **Подготовка окружения** — поскольку без корректно установленных инструментов невозможно ни локальное развёртывание, ни миграция.
- **Возможные проблемы и их решение** — на основе опыта эксплуатации мы собрали типичные ошибки (например, неверный SSL-сертификат, проблемы с сетевыми правилами) и способы их устранения.
- **Восстановление из бэкапа** — описание процесса восстановления данных из AWS S3 в случае сбоя.
- **Автоматизация с помощью Terraform** — код инфраструктуры как артефакт, который можно повторно использовать.

Эти дополнения делают проект более завершённым и готовым к использованию другими командами.

## Заключение

Данный проект демонстрирует полный цикл: от локальной разработки до промышленной эксплуатации в облаке с использованием современных подходов DevOps. Все компоненты максимально автоматизированы, что позволяет быстро восстанавливать систему после сбоев и масштабировать её по мере роста нагрузки.

Репозиторий содержит все необходимые файлы:
- `docker-compose.yml` — для локального запуска.
- `terraform/` — для развёртывания инфраструктуры в Yandex Cloud.
- `scripts/` — для миграции данных, развёртывания и бэкапов.
- `config/` — конфигурации Nginx, Prometheus, Grafana, Alertmanager.
- `.env.example` — шаблон переменных окружения.
